# TenderSniper Lite (Алматы): изменения v5.3 → v5.4

Исправленный workflow: `dist/TenderSniper_Lite_Almaty.json`, собирается командой `python3 build.py` из `src/`.
Исходник для сравнения: `original/TenderSniper_Lite_Almaty.original.json`.
Тесты: `node test/run_tests.js`, 31 проверка на моках ЦЭФ и Gemini (запускать **не** на рабочем сервере, см. инструкцию).

Для наглядности тот же набор тестовых лотов прогнали через старый и новый Pre-Filter:

| | Найдено лотов с кандидатами |
|---|---|
| v5.3 | 5 из 11 допустимых: L-PC, L-REJ, L-UPS, L-POE, L-BADCODE |
| v5.4 | 11 из 11: плюс ноутбук, МФУ, монитор, роутер, проектор, веб-камера |

Мелкие правки:
- Тексты справки и дайджеста берутся из одного конфига (`src/lib/config.js`), порог «48 ч» написан одинаково везде.
- Удалён мёртвый код (`checkDeterministicCompliance`, `lastScanTime`).
- `RE_FURNITURE` проверяет целые слова («настольный» больше не мебель). Серверный или телекоммуникационный шкаф больше не считается мебелью.
- У комплектов сохраняются дистрибьютор и признак устаревшего каталога.
- Вердикт обрезается до 350 символов, длина сообщения не больше 4096.
- В дайджесте есть сводка: сбои Gemini, ручная проверка, вендор-локи, отклонённые, отложенные, ошибки ЦЭФ.

## Найдено дополнительно при исправлении

- В каталоге `кран` (бытовая техника) совпадал внутри «эКРАН», а «креплен» внутри «VESA крепление». Мониторы и ноутбуки с такими словами в полном описании становились аксессуарами. Исправлено: проверяется начало короткого названия и целые слова.
- «Стартовый картридж» из PDF превращал любой принтер в комплект. Теперь комплект определяется по названию и описанию, стартовый картридж не учитывается.
- Комплект «ПК + монитор» одновременно требовал от товара быть и ПК, и монитором, поэтому кандидатов не было. Исправлено.
- Категория лота теперь определяется по названию и краткому описанию с портала, а не по всему тексту PDF. Текст PDF используется для поиска товаров и требований (A3, PoE, цветность).
- Разбор цены каталога: дилерская или закупочная цена в приоритете, розничная, РРЦ и уценка игнорируются. `код` не путается со штрихкодом, `арт` не совпадает внутри «к**арт**ридж».

## Изменения поведения, о которых нужно знать

- Лот, проверенный ИИ, повторно не проверяется 7 дней (`CHECKED_TTL_DAYS`). Отправленный в дайджест не показывается 120 дней, даже если запись в Google Sheets не удалась.
- Лот помечается отправленным в момент формирования дайджеста. Если Telegram не доставит сообщение и после 3 повторов, лот не придёт повторно. Он останется в листе «Кандидаты Алматы».
- Дайджест может состоять из нескольких сообщений, в конце идёт сводка.
- Колонки Google Sheets не менялись. В `rawLotId` теперь пишется ID объявления, дедлайн добавлен в колонку `Статус`.
- Новые файлы в `/home/node/.n8n/`: `tendersniper_registry.json`, `tendersniper_scan.lock` (временный).
- Необязательные переменные окружения: `GEMINI_MODEL` (по умолчанию `gemini-3.8-flash`), `USD_KZT_RATE`.

## Что НЕ менялось (нужно решение или проверка на живом API)

- Коды статусов лотов `[110, 210, 220, 230, 240]` и справочник способов закупки в `getMethodName`: проверить по справочникам портала (скрипт выводит `refTradeMethodsId` из реальных лотов).
- Исключение способов закупки: `EXCLUDE_TRADE_METHOD_IDS` в `src/lib/config.js`, по умолчанию пусто (например, «из одного источника»).
- Фильтра по региону в самом GraphQL-запросе нет, потому что поддержка фильтра по КАТО не подтверждена. Фильтр работает на стороне узла, пагинация компенсирует.
- Сканеры по-прежнему классифицируются как МФУ (как было).
- Остатки на складе не учитываются (по замыслу режима «Соло»).
- Единицы измерения (метры кабеля против цены за бухту) не сверяются.

# v5.4.1 → v5.5: радар демпинга

- Лоты без объявления о закупке (`TrdBuy: null`, пункт плана) пропускаются. Правило основано на данных, а не на коде статуса 110.
- **Radar Collector** (`dist/TenderSniper_Radar_Collector.json`, `src/radar_collector.js`) — отдельный workflow, ночью раз в час.
  Собирает итоги закупок Алматы из API ЦЭФ:
  - `Lots` по ИТ-ключевым словам (все статусы, только КАТО 75*) и договоры заказчиков (`Contract` по `customerBin`) дают очередь объявлений;
  - по каждому объявлению: `Contract` (победитель, `ContractUnits.lotId`), `Lots` (бюджет, флаг `dumping`), `TrdApp.AppLots` (сумма заявки каждого участника);
  - названия частых участников берутся из `Subjects`;
  - объявления без договора перепроверяются через 7 дней, максимум 4 раза. Своя блокировка, каждый запуск не дольше ~4 минут.
- **Оценка риска** (`src/lib/radar.js`) рассчитывается по истории заказчика в категории, затем по всем закупкам заказчика, затем по категории и похожему бюджету в Алматы:
  - медиана и разброс скидки победителя, среднее число участников;
  - частые соперники у заказчика; ⚠️ — демпингёр (стартовый список владельца или медианная скидка ≥ 30%);
  - результат при ожидаемой цене победителя и безубыточная цена (налог СНР от выручки).
  - Риск 🔴 если при ожидаемой цене убыток; 🟠 если среди соперников демпингёр или запас меньше 3 п.п.; 🟢 иначе; ❔ если истории нет.
- **Дайджест.** Под каждым лотом появляется блок «⚔️ Риск демпинга», в колонку `Статус` таблицы добавляется уровень риска. Без базы радара дайджест работает как раньше.
- `/status` показывает размер базы радара.
- В запрос лотов добавлено поле `customerBin` (есть в схеме `Lots`, проверено отчётом API).
- Тесты: `test/run_radar_tests.js`, 13 проверок, включая реальный пример 17454510 (бюджет 80 000 → победа 70 705, скидка 11,6%).

# v5.5 → v5.6: перенос серверных правок CLI + исправления

Правки, которые CLI внёс прямо на сервере (выгрузка `3FFVZUREP8jZfilm`), перенесены в исходники:
- **Матричная проверка ТЗ.** Шаг 1 (Document Extraction): ТЗ превращается в список требований с разметкой ловушек и кэшируется в `{lotId}_spec.json`. Шаг 2 (Gemini): матрица «fulfilled / failed / no_data» с цитатами. Решение принимает код (Parse): любой failed — отказ, обязательный no_data — 🟡 ручная проверка, всё fulfilled — 🟢.
- `.docx` читается в коде без Gemini. В промпт идёт только русский текст. Режим размышления `medium` (переменная `GEMINI_THINKING_LEVEL`). Кандидаты передаются с полными характеристиками (до 1500 символов). `MIN_LOT_BUDGET = 0`.

Исправлено в этих правках:
- 🔴 Промпт комплекта ссылался на переменные одиночной ветки (`candidatePayload`, `compressedLotSpec`). Первый же комплект ронял весь запуск. Теперь у комплекта свой промпт со списками основного оборудования и расходников.
- 🟠 Матрица перекрывала стоп-сигналы: «🔴 ТРЕБУЕТСЯ VAD» или «РИСК РНУ» при полностью выполненной матрице давали 🟢. Теперь стоп-сигнал всегда даёт отказ. Возвращены правила о подмене класса, VAD и письмах производителя, коррупционных маркерах и бренде без эквивалента.
- 🟠 `.docx` читался по размеру из локального заголовка ZIP. При data descriptor размер там 0, и текст терялся. Теперь размер берётся из центрального каталога.
- 🟠 Для лотов со старым текстовым кэшем структура ТЗ не строилась никогда. Теперь достраивается (до 30 за запуск).
- 🟡 Фильтр казахского выбрасывал двуязычные строки таблиц ТТХ. Строки с цифрами или латиницей теперь сохраняются.
- 🟡 Пустой результат структуры тоже кэшируется, чтобы не повторять вызов. Кэш `_spec.json` чистится вместе с текстовым.

Найдено дополнительно (было и в v5.3):
- Лот «МФУ и картриджи» считался закупкой одних картриджей, и комплекты «устройство + расходники» никогда не собирались. Теперь «лот только на расходники» — это расходник в названии без самого устройства («картридж **для принтера**» — по-прежнему расходник).

Расписание под часы работы сервера (ноутбук ~09:00–17:00 и ~20:00–23:00):
- основной бот: 09:30, 13:00 и 20:20 (узел `Schedule (09:30, 13:00, 20:20 Almaty)`, тексты `/help` и дайджеста берутся из `SCAN_TIMES_TEXT`);
- Radar Collector: `10,30,50 20-22 * * *`.

Тесты: основной набор 37 (добавлены комплект, стоп-сигнал VAD, no_data → ручная проверка, `.docx` с data descriptor, достройка структуры из старого кэша), радар 13.

# v5.6.2 → v5.6.3: диагностика «почему мало лотов»

По воронке с живого сервера (execution 638): 48 лотов Алматы → 33 уже проверены → 15 новых → 10 с товаром → **все 10 убыточны при −10%** → 0 в ИИ.
- Гипотеза о регистре не подтвердилась: API ищет без учёта регистра (0 лотов «только с заглавной»). Поиск по вариантам написания убран, ~55 лишних запросов больше не делаются.
- **Каталог.** Ночная синхронизация обновляет только `alstyle_catalog_cache.json`, а `multi_catalog_cache.json` не обновлялся с 21.09, и бот считал по старым ценам. Теперь цены Al-Style берутся из более свежего файла, а ASBIS — из мультикаталога. В дайджесте показывается возраст каждого источника.
- **Дайджест.** Добавлен блок «💸 Убыточные при −10%»: бюджет за штуку против нашей лучшей закупки за штуку, до 5 лотов. Так видно, что причина: дорогой каталог или низкий бюджет.
- Тесты: основной набор 40, радар 13.
